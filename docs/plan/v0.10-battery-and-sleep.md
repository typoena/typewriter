## Power switch + power path — decided 2026-07-26

A **latching panel switch + soft-power latch**, on top of a **power-path
(load-sharing)** circuit. Revised 2026-07-26 from the initial latching
hard-cut design: e-ink keeps its last frame when power dies, so a hard cut
leaves the panel *lying* about the power state (last text on screen, device
dead). Soft power flips that into the indicator — on shutdown, firmware paints
a **sleeping-Typo off card** and then releases its own power. The persistent
panel *is* the power display. (2026-08-03: the bought switch is latching, but
it stays a **gate signal only**, never in the load path — switch position =
desired state, and firmware still shuts down cleanly on flip-off, so the
hard-cut objection doesn't apply.)

> **Screen truth table** — sleeping Typo = off. Anything else = on (possibly
> asleep; a keypress wakes it). Zero display power either way.

The button sits next to the µSD slot on PCB2 (the case gets updated to match
the chosen part, not the reverse). Behavior contract, by state:

1. **Off, on mains** → device off, battery charges (unloaded, terminates
   cleanly). Standby drain ≈ DW01 protection only (µA) — the latch holds the
   load path fully open.
2. **On, on mains** → device runs **from mains**; the battery charges
   untouched — zero cycles spent while docked.
3. **On, mains pulled** → instant (µs, body-diode) switchover to battery; no
   brownout, nothing to detect in firmware.
4. **Flip on while off** → the closed switch pulls the latch gate low, the
   boost powers the ESP32, and `app_main` asserts `PWR_HOLD` as its **first
   statement**. The switch stays closed, so the gate is held through boot —
   no press-stretch timing to worry about.
5. **Flip off while on** → power does *not* drop (`PWR_HOLD` still holds the
   latch); firmware sees `PWR_SENSE` go high and runs the shutdown sequence:
   final save → SD unmount → paint the sleeping-Typo card → drop `PWR_HOLD` →
   dead. A clean shutdown every time, instead of the guaranteed power-pull a
   mechanical cut would be. (Bonus over momentary: a crashed ESP32 releases
   `PWR_HOLD` but the closed switch keeps the gate low — it reboots instead
   of dying mid-write.)

The HW-373 alone can't do the mains-priority part: its OUT pins feed the load
*through the battery path*, so a docked, running device would micro-cycle the
cell and the TP4056 would never terminate. Load share fixes that; the latch
replaces the mechanical switch in the load path:

```
USB-C mains ──5V──┬────────────► TP4056 (HW-373) ──B+──► [JST-PH] LiPo 3700 mAh
                  │                                          │
                  │ SS34 Schottky                            │ (OUT+, via DW01 FETs)
                  ▼                                          ▼
                  ├◄──────────── AO3401 #1 (load share) ◄────┘
                  │              gate → 5V mains, 100k pulldown
                  ▼
            [load node] ──► AO3401 #2 (soft latch) ──► MT3608 ──► 5V rail
                                 │ gate ─ 100k pull-up → load node (default OFF)
                                 ├─◄ 1N4148 ◄─ [SW] latching switch → GND
                                 └─◄ 2N7002 drain, gate ← PWR_HOLD (100k pulldown)
                              [SW] ─ 10k series → PWR_SENSE GPIO (internal pull-up)
```

Mains present holds load-share gate high (off) and feeds the load through the
Schottky (~4.7 V into the boost — fine, it only ever steps up); mains gone, the
body diode conducts immediately, then the gate falls and the FET carries the
battery current at low loss. The latch FET defaults off via its gate pull-up
(zero quiescent); the switch *or* the 2N7002 (driven by `PWR_HOLD`) pulls the
gate low to conduct.

**Placement rules (invariants):**

- The latch cuts the **load path only** (load node → MT3608 input). Never put
  it between battery and charger, or state 1 stops charging.
- Battery is hard-wired to B+/B− — its charge path has no switch, no diode.
- The **switch carries gate signal only** (µA) — its current rating is
  irrelevant. Its LED stays **unwired**: fed from the switched 5 V rail it
  stays lit through sleep, and 3–6 mA caps lid-closed standby at ~25–50 days
  on the 3700 mAh cell — the screen truth table already shows power state.
- The `PWR_HOLD` → 2N7002 gate takes a **100k pulldown** so a crashed/reset
  ESP32 (floating GPIO) releases the latch rather than wedging it on.
- `PWR_SENSE` takes a **10k series resistor**: while off, the latch pull-up
  back-feeds ~µA through the button diode toward the unpowered ESP32 pin; the
  series R caps the injection.
- The **≥ 100 nF gate cap** existed to stretch a momentary press across the
  ~0.5 s boot-to-`PWR_HOLD` window; the latching switch holds the gate itself,
  so the cap is moot — harmless to fit, safe to omit.

**Hazards:**

- ⚠️ JST **polarity is not standardized** across battery vendors — verify red
  lands on B+ against the PCB2 footprint before first plug-in; a reversed pack
  kills the charger board.
- ⚠️ **A hung firmware can't be powered off** — the latch only releases via
  `PWR_HOLD` (or a reset dropping the GPIO to its pulldown). Recovery is the
  devkit reset/battery pull. If this bites in practice, the upgrade path is a
  pushbutton controller IC (e.g. LTC2954: built-in 14 s force-off; ~€4,
  Mouser — not an Amazon part).
- The shutdown sequence must **save + unmount before painting the off card**,
  and release `PWR_HOLD` only after the refresh completes — the card is baked
  in flash, no SD needed to draw it.
- The button needs ~20 mm of body depth behind the panel plus wire clearance —
  check against the PCB2/case pocket before freezing the case update. Hole is
  Ø12 mm.
- The sleeping-Typo card is a new `display::typo` mood if the shuffle-bag
  doesn't already have one — same `typogen.py` pipeline, derived from the
  reference image like every Typo asset.
